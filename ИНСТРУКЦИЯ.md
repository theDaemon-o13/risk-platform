# Инструкция по развёртыванию и эксплуатации — Risk Platform

Документ для администратора/оператора. Описывает полный цикл: сборка → перенос в изолированную сеть → установка → обновление → резервное копирование.

---

## 0. Что вы устанавливаете

Три контейнера, управляемые одним `docker compose`:

| Контейнер | Назначение | Порт |
|-----------|------------|------|
| `risk-platform-web` | веб-интерфейс (nginx + статика) | 80 (наружу) |
| `risk-platform-api` | сервер приложения (Node.js) | 3000 (внутри сети) |
| `risk-platform-db`  | база данных (PostgreSQL) | 5432 (внутри сети) |

Данные хранятся в **Docker volume `risk-platform-db-data`** и **не теряются** при обновлении.

Нужны две машины:
- **Машина-сборщик** — с доступом в интернет (собирает образы).
- **Целевая машина** — изолированная, где платформа будет работать. Интернет и git не нужны.

> Если интернет есть прямо на целевой машине — можно собрать там же, шаги переноса (часть Б) пропускаются.

---

## 1. Требования

**Машина-сборщик:**
- Docker 24+ и Docker Compose v2 (`docker compose version`)
- Доступ в интернет (тянет базовые образы `postgres`, `nginx`, `node`)
- Git/Node для разработки **не обязательны** — сборка идёт внутри Docker

**Целевая машина (Linux):**
- Docker 24+ и Docker Compose v2
- ~2 ГБ свободной RAM, ~5 ГБ диска
- Открытый порт 80 (или другой — настраивается)

Проверка наличия Docker:
```bash
docker --version
docker compose version
```

---

## 2. Часть А — Сборка релиза (на машине-сборщике)

1. Скопируйте папку проекта `risk-platform/` на машину-сборщик (любым способом).

2. Создайте файл секретов из шаблона:
   ```bash
   cd risk-platform
   cp config/app.env.example config/app.env
   ```

3. Откройте `config/app.env` и заполните **обязательные** поля:
   ```ini
   POSTGRES_USER=risk_platform
   POSTGRES_PASSWORD=<придумайте надёжный пароль БД>
   POSTGRES_DB=risk_platform

   JWT_SECRET=<случайная строка 32+ символа>
   INITIAL_ADMIN_USERNAME=admin
   INITIAL_ADMIN_PASSWORD=<пароль первого админа>
   ```
   Сгенерировать `JWT_SECRET` (на Linux/Mac):
   ```bash
   openssl rand -base64 48
   ```

4. Соберите релизный архив:
   ```bash
   make pack
   ```
   Результат — файл вида `release-YYYYMMDD-HHMM.tar.gz` (внутри все 4 образа).

   > Если `make` недоступен: `bash scripts/build-offline.sh`

---

## 3. Часть Б — Перенос на целевую машину

Скопируйте на изолированную машину (флешка / защищённый канал) **четыре вещи**:

```
release-YYYYMMDD-HHMM.tar.gz     ← образы
docker-compose.yml               ← описание стека
config/                          ← вся папка (app.env, nginx.conf, frontend.js)
scripts/  и  Makefile            ← команды управления
```

Разложите их в одну папку, например `/opt/risk-platform/`, сохранив структуру (`config/`, `scripts/` — подпапками).

> ⚠️ Файл `config/app.env` содержит пароли. Перенесите его защищённо и проверьте права: `chmod 600 config/app.env`.

---

## 4. Часть В — Первая установка (на целевой машине)

```bash
cd /opt/risk-platform

# 1. Убедитесь, что config/app.env на месте и заполнен
cat config/app.env

# 2. Установка
make deploy FILE=release-YYYYMMDD-HHMM.tar.gz
```

Что делает команда:
1. `docker load` — загружает образы из архива;
2. `docker compose up -d` — поднимает db → api → web;
3. api при первом старте создаёт таблицы, системные роли, справочники и учётку администратора.

Проверка:
```bash
make ps                       # все три контейнера должны быть "Up"
curl http://localhost/api/health   # {"ok":true,...}
```

> Если `make` недоступен: `bash scripts/deploy.sh release-YYYYMMDD-HHMM.tar.gz`

---

## 5. Первый вход

1. Откройте в браузере: `http://<адрес-целевой-машины>/`
2. Логин — значения из `config/app.env`:
   - имя: `INITIAL_ADMIN_USERNAME` (по умолчанию `admin`)
   - пароль: `INITIAL_ADMIN_PASSWORD`
3. Зайдите в раздел **Пользователи** и заведите реальные учётные записи сотрудникам, назначьте роли.
4. Рекомендуется сменить пароль администратора после первого входа.

> Учётка администратора создаётся **только один раз** — при первом запуске с пустой БД. При последующих стартах переменные `INITIAL_ADMIN_*` игнорируются.

---

## 6. Часть Г — Обновление версии (без потери данных)

На машине-сборщике соберите новый релиз (`make pack`) и перенесите новый `release-*.tar.gz` на целевую машину.

На целевой машине:
```bash
cd /opt/risk-platform
make update FILE=release-NEW.tar.gz
```

Что делает команда:
1. **Автоматически снимает бэкап БД** в `backups/` (страховка);
2. `docker load` — загружает новые образы;
3. пересоздаёт **только** `api` и `web`. Контейнер `db` и volume с данными **не трогаются**;
4. api применяет новые миграции БД (если есть) — данные сохраняются.

Проверка после обновления:
```bash
make ps
make logs        # Ctrl+C для выхода
```

> Откат: если что-то пошло не так — восстановите БД из бэкапа (часть Е) и загрузите предыдущий `release-*.tar.gz` через `make update`.

---

## 7. Часть Д — Изменение конфигов (без пересборки)

Все настройки — в папке `config/` на целевой машине. Менять можно прямо там.

| Файл | Что настраивает | Как применить |
|------|-----------------|---------------|
| `config/nginx.conf` | заголовки, кеш, маршруты, лимиты загрузки | `docker compose --env-file config/app.env restart web` |
| `config/frontend.js` | имя организации, тайм-аут сессии, адрес API | обновить страницу в браузере (Ctrl+Shift+R) |
| `config/app.env` | пароли, `JWT_SECRET`, порт, уровень логов | `docker compose --env-file config/app.env up -d` |

Пример — сменить порт веб-интерфейса на 8080: в `config/app.env` добавьте `WEB_PORT=8080`, затем `docker compose --env-file config/app.env up -d`.

> **Справочники** (типы инцидентов, серьёзности, риск-аппетит и т.п.) меняются **внутри платформы** в разделе «Справочники» — они хранятся в БД и переживают обновления автоматически.

## 8. Часть Е — Резервное копирование и восстановление

**Сделать бэкап вручную:**
```bash
make backup
# → backups/risk-platform-YYYYMMDD-HHMMSS.sql.gz
```

**Восстановить из бэкапа:**
```bash
make restore FILE=backups/risk-platform-YYYYMMDD-HHMMSS.sql.gz
```
(спросит подтверждение, остановит api, зальёт дамп, запустит api обратно)

**Автоматический бэкап по расписанию** (cron на целевой машине, ежедневно в 02:00):
```bash
crontab -e
# добавить строку:
0 2 * * * cd /opt/risk-platform && make backup >> /var/log/risk-backup.log 2>&1
```
Бэкапы старше 30 дней удаляются автоматически.

## 9. Часть Ж — Частые команды

```bash
make ps        # статус контейнеров
make logs      # логи всех сервисов (Ctrl+C — выход)
make down      # остановить стек (данные БД сохраняются)
make backup    # дамп БД
make help      # список всех команд
```

Перезапуск одного сервиса:
```bash
docker compose --env-file config/app.env restart api
```

## 10. Диагностика проблем

| Симптом | Причина / решение |
|---------|-------------------|
| `make ps` показывает `api` как `Restarting` | api не достучался до БД. Смотрите `docker compose --env-file config/app.env logs api`. Обычно — неверные `POSTGRES_*` в `config/app.env`. |
| Браузер: «502 Bad Gateway» | `api` ещё стартует или упал. Подождите 10–20 сек / смотрите логи api. |
| Не пускает первого админа | Проверьте `INITIAL_ADMIN_*` в `app.env`. Если БД уже была создана раньше — учётка не пересоздаётся; заведите/сбросьте через другого админа или восстановите из бэкапа. |
| «Переменная POSTGRES_USER не подставилась» | Все команды должны идти с `--env-file config/app.env`. `make`-команды и скрипты делают это сами; ручные вызовы `docker compose` — добавляйте флаг. |
| Порт 80 занят | Задайте `WEB_PORT=8080` в `app.env` и `docker compose --env-file config/app.env up -d`. |
| Нужно посмотреть, что в БД | `docker compose --env-file config/app.env exec db psql -U <POSTGRES_USER> -d <POSTGRES_DB>` |

**Полная переустановка с нуля (⚠️ удаляет ВСЕ данные):**
```bash
make clean        # спросит подтверждение, удалит контейнеры + volume БД
make deploy FILE=release-*.tar.gz
```
